# A better controller, without touching the Pi

Written 2026-10-15 after a day of poking the server (facts in `arclamp-api.md`). The brief:
the server stays as it is; everything new runs in a browser on my Mac.

## 1. What's wrong now

### Server design (can't change, must design around)

1. **Code is the only parameter channel.** The one way to change anything about a running
   layer is to re-upload its whole script, which recompiles V8 (0.15–2 s) and stalls other
   requests. There is no "set this value" for a layer. A knob that drives an animation is
   therefore a knob that recompiles code.
2. **Layers compose by replace only.** No opacity, no blend, no crossfade, no master dimmer.
   "Fade from look A to look B" cannot be expressed to the server; whichever layer is on top
   simply wins. Transitions have to be faked inside one script.
3. **Wall-clock time is the only input a layer gets.** Nothing from outside (MIDI, audio,
   sensors, a slider) reaches a running script except by rewriting it.
4. **No names, groups, layout or presets.** Layers are auto-incremented ids whose only label is
   their source code. Lights have empty `tags` and `coords`. The scene *is* the state; there is
   no snapshot to save or recall.
5. **The roomtone is global mutable state** that any client on the LAN can overwrite, with no
   history. (The TouchDesigner bridge has a `restore` command purely because of this.)
6. **Append-only ergonomics.** "Send demo" adds a layer and nothing removes one; the vocabulary
   is inverted (`position: "bottom"` creates the top-most, winning layer); the result is the
   18-deep pile of identical demos the scene has right now.
7. **Performance degrades silently and badly.** Clean: ~100 ticks/s, 35 fps stream, ~85 ms
   write. With 18 layers: <25 ticks/s, ~10 fps, and a write takes **1.4 s to become visible**.
   Concurrent writes can stall it for seconds. The server never says "busy"; you find out by
   watching the lights lag.
8. **The relay channel lies.** 52 fixtures advertise an 8-bit `brightness` that is physically a
   switch.
9. **One shared demo token, printed in a public page.** Identity = token, so every client is
   "demo" and there's no per-client ownership of layers.
10. **The stream is all or nothing**: every light every frame, 9 KB as JSON, or a binary format
    that needs the channel-order table from `/v1/lights` to decode.

### The debug page

A table of numbers with no spatial view; layer labels are the first 60 characters of source;
the roomtone sliders hit every light at once; no undo, no presets, no selection; and it leads
with a code editor, so the first thing it teaches is "write JavaScript."

### What's actually good (and the whole design leans on it)

- **`prev` is the composited frame *below* a layer**, not its own last output, and **scripts
  keep state between ticks**. So a layer at the top can read the roomtone as a set of targets
  and ease its own output toward them. That one fact turns the cheap write path into a smooth
  one.
- Partial roomtone writes are cheap (~85 ms), merge per channel, and persist.
- CORS is open and auth is one header, so a static HTML file anywhere on the LAN is a client.
- `curr` is wall-clock, so re-uploading a script resumes in phase and layers stay phase-locked.
- "Blank means merge": a layer that only lists some lights leaves the rest to others, so two
  controllers can share the room by id range.

## 2. The better system

**Principle:** the Pi runs exactly two things of ours. The **roomtone is a target buffer** we
write at up to 10 Hz, and one **engine layer** at the top, generated by the browser, turns
those targets into smooth, animated output. Everything else (looks, parameters, MIDI, presets,
layout, transitions, undo) lives in the page.

```
MIDI / mouse / keyboard / OSC-from-TD
        │
        ▼
  controller page (Chrome, served from localhost)
        │  ├─ write scheduler: coalesce per light+channel, latest wins, ≤10 Hz ──► PUT /v1/shader/0  (targets)
        │  └─ look compiler: look + params + selection + crossfade ──(debounced)──► PUT /v1/shader/<engine>  (rare)
        ◄──── WS /v1/scene/ws ──── floor plan colours, health meter (fps, write latency)
```

### 2.1 The engine layer

One JS layer we own, tagged with a header comment (`// arclight-engine v1`) so the page finds
and adopts it after a reload instead of creating another. It is generated code, assembled from:

- **Smoother.** Per light it keeps its own current values in script state and eases toward
  `prev` (the roomtone target) with a time constant, e.g. 150 ms. Ten target writes a second
  from a slider become a continuous fade at the server's tick rate. This alone fixes "steppy".
- **Look = modulation, not colour.** A look (breathe, chase, wave, sparkle, strobe…) computes a
  0–1 envelope per light per tick; the output is `envelope × target colour`. Colour comes from
  the fast path (roomtone, ~100 ms); movement comes from the slow path (script). A MIDI knob on
  hue feels live; switching looks takes ~0.6 s, which is fine for a pad press.
- **Crossfade baked in.** When the look or its params change, the new script contains both the
  old and the new look and mixes them over `FADE` ms using `curr - init`. The server can't fade;
  the generated code can.
- **Selection baked in.** The engine only lists the ids the user selected (or all), so it merges
  with whatever else is running and two controllers can split the room.
- **Params baked as constants.** `var SPEED = 8000, HUE_SHIFT = 0.2, IDS = [1,2,3]` at the top.
  The page never shows this code unless the user opens "advanced"; it edits the knobs and
  re-generates.

Caveat: if foreign layers sit between the roomtone and the engine, `prev` includes them. The
page lists foreign layers and offers "own the room" (mute them all) and "reset" (delete them).

### 2.2 Data that lives in the page (localStorage, exportable JSON in `web/data/`)

| file | holds |
|---|---|
| `layout.json` | id → `{x, y, group}` for the 115 lights; drag to edit on the floor plan |
| `groups.json` | named id lists ("wall A", "ceiling", "relays") |
| `looks/*.js` | look templates with declared params `{name, min, max, default, kind: "target"\|"script"}` |
| `presets.json` | `{targets, look, params, selection}`; recall = one roomtone PUT + one engine PUT |
| `midimap.json` | CC/note → what it drives |

### 2.3 Write scheduler

One queue, one in-flight request at a time, never concurrent. Target writes coalesce per
(light, channel) with latest-wins and flush at ≤10 Hz. Engine uploads debounce 300 ms and wait
for the queue to drain. If stream fps drops or PUT latency climbs past ~300 ms, the page backs
off and shows it. The server won't tell you it's overloaded, so the UI must.

### 2.4 Input: Web MIDI

- Works in Chrome and Edge (Firefox too, Safari no). **Needs a secure context**, so the page
  must be served from `localhost` (e.g. `python3 -m http.server` in `web/`) or opened as a file.
  It would *not* get MIDI if hosted on `http://arclight.local:8081`. CORS already allows this.
- Mapping, with a learn mode (wiggle a control, click a knob on screen):
  - **CC → target params** (hue, saturation, white balance, intensity, per group or selection).
    Feels ~100–200 ms on a clean server.
  - **CC → look params** (speed, width, density). Debounced; ~0.6–1 s plus the crossfade.
  - **Notes / pads → preset recall, look switch, blackout, "own the room", tap tempo.**
- OSC stays available through `~/arclamp-td/arclamp_bridge.py` for TouchDesigner; the page
  can also listen on a WebSocket from that bridge later if TD and MIDI need to coexist.

### 2.5 The screen

Floor plan with live colours from the stream; click and drag to select; group buttons; one colour
control (RGB + cold/warm) and an intensity for the selection; relay toggles; a look picker with
its knobs; preset pads; a drawer listing foreign layers with mute/delete; a health strip (stream
fps, write latency, tick-rate estimate); blackout and reset buttons. No code editor on the main
screen.

### 2.6 What this still can't fix

Other people's layers loading the server; the relays not dimming; the ~85 ms + tick latency
floor; one token and no per-client ownership. Those need server changes, and the wishlist for
whoever has the Pi is short: a `params` object per layer settable without recompiling, a
`name` field on layers, a master fader, and one token per client.
